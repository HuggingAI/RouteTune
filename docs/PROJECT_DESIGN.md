# RouteTune 精简立项方案

> 版本：v0.5
> 日期：2026-10-09
> 状态：以实验—审阅—训练—评测—发布—反馈为产品主线
>
> 最短产品说明见 [PRODUCT_ONE_PAGER.md](PRODUCT_ONE_PAGER.md)，发布与扩缩容约束见 [RELEASE_ARCHITECTURE.md](RELEASE_ARCHITECTURE.md)。

## 1. 产品宪法

RouteTune 的所有产品决策都必须通过三个问题：

1. 产品能否用一页纸介绍清楚？
2. 核心技术能否脱离当前产品形态独立发展？
3. 产品是否只有一个清晰、可传播的核心特色？

第一版的判断规则是：

> 任何不能直接帮助我们判断“哪个模型刚好够用”的功能，都不进入 MVP。

## 2. 一句话定位

> RouteTune 使用企业自己的真实业务标注，训练专用分类路由器，把每个请求交给达到质量线的最低成本模型。

传播表达：

> 把每个请求交给“刚好够用”的模型。

## 3. 解决的问题

已经接入多个模型的企业通常只有两个选择：

- 所有请求都使用昂贵的强模型，质量稳定但成本高；
- 使用人工规则或通用语义类别分流，但无法证明业务质量。

通用路由器能够识别“摘要”“代码”“问答”等任务，却不知道某个候选模型在客户自己的合同、客服、研发或运营场景中是否真的合格。

RouteTune 只解决一个核心问题：

> 在业务质量不低于约定门槛的前提下，能否通过标注驱动的模型路由显著降低推理成本？

## 4. 核心特色

RouteTune 的特色不是“支持很多模型”，也不是“拥有完整治理平台”，而是：

> 每个路由策略都由客户自己的标注和候选模型实测结果训练、校准并验证。

这项特色决定所有必要能力：

|能力|存在的唯一理由|
|---|---|
|Annotation|定义什么叫业务合格|
|Evaluation|证明哪些模型对哪些请求合格|
|专用分类器|预测各候选模型完成当前请求的成功概率|
|Routing|在合格候选中选择成本最低者|
|Trace|将请求、决策、输出和标注重新关联|
|安全|保证真实业务数据能够安全进入这条闭环|
|发布与回滚|让验证后的策略受控进入生产|

## 5. 产品闭环

```text
接入候选模型并导入真实请求
→ 运行候选模型对比实验
→ 用户或评审人员标注哪些结果合格
→ 训练候选路由器并与生产版本评测对比
→ 创建包含 Router、模型池和安全策略的不可变 Release
→ 人工发布到统一 API
→ 线上 Trace 与反馈回流下一轮实验
```

在线运行：

```text
新请求
→ 输入安全处理
→ 专用分类器预测各候选模型成功概率
→ 过滤不满足能力或安全约束的模型
→ 选择达到质量门槛的最低成本模型
→ OpenAI-compatible Adapter 执行调用
→ 输出安全处理与 Trace
```

## 6. 核心技术与产品分离

### 6.1 RouteTune Engine

核心技术作为独立 Engine 发展，不依赖 Web、数据库、Proxy 或具体模型供应商。

训练输入：

```text
请求特征
候选模型标识与能力
候选模型输出的合格/不合格标注
可选错误原因与质量分数
相对成本等级与延迟（核心验证阶段）
```

核心能力：

- 专用非生成式分类模型；
- 候选模型成功率预测；
- 概率校准；
- 分布外检测与拒识；
- 硬约束过滤；
- 质量门槛下的成本优化；
- 可解释决策；
- 不可变策略包的编译与加载。

运行输入与输出：

```text
Engine Input
  request features
  candidate snapshot
  policy bundle

Engine Output
  selected model
  candidate probabilities
  confidence / OOD
  exclusion reasons
  fallback
  version references
```

第一版核心决策可以形式化为：

```text
eligible = 满足安全、能力、区域和上下文硬约束的候选模型

在 eligible 中选择：
argmin cost(model)
subject to calibrated P(success | request, model) >= quality_threshold
```

如果没有模型达到质量门槛，或者分类器拒识，则进入确定性 fallback，而不是放宽安全约束。

### 6.2 产品外壳

产品外壳只负责让 Engine 能够获得数据并安全进入生产：

- 链路内 Enforcement Runtime；
- 简单 Annotation 界面；
- 离线候选模型执行和对比报告；
- 最小 Trace；
- 模型、分类器和策略版本管理；
- 手动发布和快速回滚；
- OpenAI-compatible Model Adapter。

未来产品即使转向 Gateway Plugin、离线顾问、SaaS 或行业解决方案，Engine 仍可独立使用。

## 7. MVP

### 7.1 试点范围

- 一个客户或内部真实业务；
- 一个明确、可计算或可人工判断的质量标准；
- 300～1000 条代表性请求；
- 2～5 个候选模型；
- 一个或多个 OpenAI-compatible Provider 配置；
- 中文优先，兼顾必要的中英混合输入；
- 单组织私有部署。

### 7.2 必须完成

1. 导入或采样真实请求；
2. 对候选模型进行离线回放；
3. 展示同一请求的候选输出；
4. 支持最小人工 Annotation；
5. 生成版本化训练数据；
6. 训练专用分类模型并校准概率；
7. 比较固定高成本模型、固定便宜模型、人工规则和 RouteTune；
8. 生成质量—成本—延迟报告；
9. 将通过验证的策略发布到链路内 Runtime；
10. 记录决策、实际调用、输出引用和后续 Annotation；
11. 支持安全回退和策略回滚。

### 7.3 最小 Annotation

MVP 只支持：

- `pass / fail`；
- 可选失败原因；
- 可选 1～5 分；
- 可选评语；
- 输出内容 Hash 和版本绑定。

第一版不做复杂任务分配、多人一致性、盲评平台和完整仲裁系统。需要多人复核时，可以通过简单的第二次 Review 实现。

`Annotation` 是人主动评价某个确定输出；`Outcome` 是重试、采纳、投诉、流程成功等自然业务结果。二者分开保存。

### 7.4 最小路由策略

MVP 只实现一个主策略：

> 在预测达到质量门槛的候选模型中选择成本等级最低者。

同时保留三个对照基线：

- 全部使用最强模型；
- 全部使用最便宜模型；
- 当前人工规则或固定模型。

不在 MVP 同时提供大量策略模板。

## 8. 链路内 Runtime

RouteTune 必须位于实际数据路径，才能执行输入出域脱敏和输出保护：

```text
业务系统
→ RouteTune Enforcement Runtime
→ OpenAI-compatible Provider API
→ 模型供应商
```

Runtime 是薄代理，不是通用 LLM Gateway：

- 只支持一种受控兼容协议；
- 只支持无状态单轮 `messages` 输入和单条 assistant response；
- 通过统一协议连接已配置的 Provider；
- 不实现各供应商专用 SDK；
- 不负责供应商负载均衡、业务重试和熔断；
- 负责安全处理、Engine 调用、模型字段注入、非流式响应和 Trace。

## 9. 安全基线

安全是使用真实业务数据的前提，但不是独立产品方向。

MVP 只实现：

- 输入和输出检测；
- 密钥、Token、手机号、邮箱、证件号等高价值规则；
- 客户词典；
- spaCy 等传统 NER 扩展；
- 日志脱敏、出域脱敏和阻断；
- `metadata_only` 和默认的 `redacted` 存储模式。

第一版不自研通用 DLP、越狱检测基础模型或合规平台。检测器只返回位置、类型、置信度和版本，动作由安全策略决定。

## 10. 最小 Trace

每个请求只要求能够关联：

```text
request_received
security_processed
classification_completed
route_decided
model_call_completed
response_processed
request_completed
outcome_received / annotation_created
```

Trace 的目的不是建设通用观测平台，而是回答：

- 当时为什么选择这个模型？
- 实际调用了哪个部署？
- 输出是否被判定为合格？
- 策略相比固定高成本模型是否真正减少高成本调用？

密钥、Cookie、密码和访问令牌永不进入日志。

## 11. 明确不做

MVP 不做：

- 通用多供应商 LLM Gateway；
- 完整 OpenAI API 覆盖；
- 通用 Annotation 平台；
- 通用 DLP 或内容安全平台；
- RAG、Agent、知识库和 Prompt 管理；
- SaaS 强多租户；
- 自动在线强化学习；
- 大量路由策略模板；
- 复杂 RBAC、审批流和计费；
- 同时维护多个 Gateway Plugin；
- 未经人工确认自动发布生产策略。

## 12. 成功与停止条件

### 12.1 必须报告

- 业务质量通过率；
- 达到质量门槛时的高成本模型避用率；
- 各成本等级模型的选择比例；
- 相比当前策略的质量变化；
- 分类器校准误差、拒识率和额外延迟；
- 每个候选模型的选择比例；
- 置信区间和样本量。

### 12.2 试点成功

成功门槛由试点前明确，但至少满足：

- 质量下降不超过业务允许范围；
- 成本节省具有实际价值，并覆盖 Runtime 与维护成本；
- 路由效果显著优于简单人工规则；
- 结果在留出集和 Shadow 流量上仍成立；
- 客户愿意继续提供标注并使用该策略。

### 12.3 停止或转向

出现以下情况时不继续堆功能：

- 强弱模型在真实任务上没有稳定质量差异；
- 用简单规则已经能够取得近似收益；
- 所需标注成本超过可节省的推理成本；
- 分类器无法可靠校准或拒识；
- 客户只需要网关基础能力，不需要数据驱动路由；
- Inline Runtime 的延迟或运维成本无法接受。

## 13. 验证与实施顺序

### 阶段 0：核心技术验证

先在离线数据上完成最小闭环：

```text
EvaluationRecord 数据契约
→ 候选输出与 pass/fail 标注
→ 成功率分类器
→ 概率校准
→ 质量门槛最低成本策略
→ 与三个基线比较
```

阶段 0 不建设正式 Web、Proxy 或复杂数据库。

阶段 0 已完成：合成数据闭环与公开数据双模型 smoke 均已跑通。公开 benchmark 不再继续扩充，也不作为产品价值证明。

### 阶段 1：最小产品（已完成）

- EvaluationRecord 数据导入；
- 候选模型执行；
- 简单 Annotation 页面；
- 报告；
- Engine 模型包和策略包；
- Bundle 文件的手动选择与启动。

### 阶段 2：受控在线试点基础（已完成）

- 薄 Enforcement Runtime；
- 输入/输出安全基线；
- OpenAI-compatible Adapter；
- Trace 和 Outcome；
- 冷启动 fallback 与训练 Bundle 切换。

### 阶段 3：产品闭环与受控发布（进行中）

- 工作台以完整路由优化周期组织，而不是按技术模块组织；
- 模型池与安全策略作为草稿编辑；
- Router、模型池和安全策略形成不可变 Release；
- `production` Deployment 只指向已发布 Release；
- 统一 API 与 Trace 固定绑定活动版本；
- 支持发布和回滚；
- 补齐独立 Experiment、评测门禁和反馈样本队列。

完成上述闭环后，只有在真实规模需求出现时，才引入复杂 Annotation、审批流、多租户、消息队列或微服务拆分。

## 14. 当前实现与下一步

Engine、公开基准执行器和在线纵切面已经完成。开源版提供统一请求入口、安全脱敏、分类路由、真实模型调用、失败回退、SQLite Trace、人工标注，以及候选 Release、Production 发布和回滚。

下一步不横向扩模块，而是补齐独立 Experiment 与评测门禁，让用户无需理解内部模块即可完成一次“实验 → 审阅 → 训练 → 对比 → 发布 → 反馈”的完整周期。公开数据只保留为回归 smoke；真正的训练数据最终来自产品中的真实请求、候选输出与用户 pass/fail 标注。
